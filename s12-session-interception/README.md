## The range-filter trap

The wrong form, entered when the intent was "only the target":

```text
ip.addr == 10.0.2.0/24
```

```text
<<REPLACE with the wrong-form frame count>>
```

The wrong form returned nearly the whole capture. `ip.addr` is a combined field that matches EITHER the source OR the destination address, so with a CIDR range it matches every frame where any address in the range appears on either side: traffic to the NAT gateway, gateway replies, and traffic between the attacker and the target all match at once. The correct form states the intent on one field: `ip.src == 10.0.2.5` for traffic from the target only, or `ip.addr == 10.0.2.5` used deliberately when both directions are wanted.

## Cookie flag assessment

```bash
curl -sI http://10.0.2.5/dvwa/login.php | grep -i set-cookie
```

```text
Set-Cookie: PHPSESSID=...; path=/
```

The DVWA session cookie carries none of the three hardening flags, and each missing flag maps to a specific attack demonstrated or enabled in this report:

| Missing flag | Attack it enables | Evidence in this report |
|---|---|---|
| **Secure** | The cookie travels over plain HTTP, so anyone on the segment captures it | Part B credential and cookie extraction |
| **HttpOnly** | JavaScript reads `document.cookie`, so the DVWA XSS pages (Reflected, Stored) steal the session | DVWA XSS modules, same lab |
| **SameSite** | The cookie rides on cross-site requests, enabling CSRF against authenticated actions | DVWA CSRF module, same lab |

# Part C - Man in the middle (15 marks)

## The working ARP-poisoning MITM

```bash
sudo apt install -y dsniff
sudo arpspoof -i eth0 -t 10.0.2.5 10.0.2.2     # terminal 1: victim, you are the gateway
sudo arpspoof -i eth0 -t 10.0.2.2 10.0.2.5     # terminal 2: gateway, you are the victim
sudo sysctl -w net.ipv4.ip_forward=1           # terminal 3: relay packets
```

## Why ip_forward is required

The poisoned ARP entries send the victim's packets to the attacker instead of the gateway, and the gateway's replies to the victim. Without forwarding, the attacker receives the packets and silently drops them: the victim's internet dies, which is an availability attack, not interception. With `net.ipv4.ip_forward=1`, the attacker relays every packet between victim and gateway while reading or modifying it, and the victim sees normal connectivity, which is what makes the interception invisible.

## Three client controls, in deployment order

1. **TLS on the web application (HTTPS everywhere)** - stops the cleartext credential and cookie capture from Part B and the plain-HTTP interception in Part C, because the attacker sees only encrypted bytes. It does not stop ARP poisoning: the attacker still relays the traffic, just without reading it.
2. **Dynamic ARP inspection with static gateway entries on the switch** - stops the ARP poisoning itself: the switch rejects ARP replies whose sender address does not match its binding table. It does not stop a rogue machine that never sends ARP, and it must be configured per switch port.
3. **802.1X port authentication at the edge** - stops the rogue attacker machine from joining the segment in the first place, before any layer-2 or layer-7 attack exists. It does not protect against an already-authorised machine that is compromised, and it requires infrastructure (RADIUS) beyond the switch.

The order matters: 802.1X first so rogue machines never join, DAI second so authorised machines cannot poison each other, TLS third so even a successful interception reads nothing.
